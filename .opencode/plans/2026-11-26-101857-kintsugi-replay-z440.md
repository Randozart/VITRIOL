# Kintsugi-27B launch and placement on the Z440

## Purpose

Qualify the fastest correct native Kintsugi-27B setup on the Z440 and assess the role of the second RTX 3060.

## Approach and alternatives

Diff the local reference and VITRIOL replay paths, reproduce with one idle GPU, localize the first CUDA failure, and apply the smallest source-backed fix. Compare existing snapshot mode to replay and evaluate two-card placement if it is viable. Keep the service and installed profile outside experiments.

- Compare single-card GPU residency, dual-card layer split, and placing only the drafter on the second card. Select on matching workload, placement, and repeatable output checks.

## Scope and documentation

The launch command lives in `scripts/serve-kintsugi.sh`. It uses the existing engine binary and loopback port. Record the chosen configuration and supported depth in this plan and link it from `AGENTS.md`.

## Verification

- Capture argv, fingerprints, slot and GPU telemetry. Require ready and a successful request; test deterministic rollback, resend and prompt change against snapshot mode before comparing speed. Check affected engine gates and Praetor for any code changes.

## Results and evidence

Placement, replay, and filled-depth results follow below. Raw flags, API responses, and sampled GPU telemetry are in `/tmp/vitriol-kintsugi-z440`. The verification runner writes its source-bound result to that directory’s `verification/` subdirectory.

## 2026-11-26T10:23:45+01:00 diagnosis

Synchronous eager CUDA reports the illegal read in F32 `ggml_cuda_op_get_rows` during the first request. `llama_memory_recurrent_context::s_copy()` adds a snapshot-plane offset on rejection. That offset applies to the R convolution history but cannot index the one-plane replay S state. The reference uses the already-ported `s_copy0` graph input for S. Use that input for replay S only, preserving normal R and snapshot gathers. A steady request alone cannot qualify replay. The pending plane is absent from the current serialization format, so checkpoint and prompt-cache behavior must be reviewed before promoting it.

### Replay hold

Using the reference row selection ended the gather crash. The experimental patch is retained outside the working tree in `replay-row-gather.patch`. The initial patched replay run reached 56.2–56.4 tok/s repeat and 29.3 code with tiered RS. Greedy text differences prompted a fixed-token check with exact output head and batch-invariant kernels. On reject-six versus clean history, the snapshot RMS logit difference was 0.01566 and the replay difference was 0.08949. Both retained the same top token for that probe. The tested replay build then failed while serializing a state immediately after rejecting six tokens, with `tensor read out of bounds`. Both the clean and post-rejection checkpoint continuations of the snapshot control matched their live logits exactly across all 248320 outputs.

Keep both replay switches off. The retained experimental row selection is only the gather repair. A replay release needs pending-state serialization, rejection handling, and correctness qualification. The resident snapshot placement already offers the faster tested operational path on this host.

## Z440 pooling decision

Keep the recurrent snapshots on the inference GPU. The existing pinned-host KV tier provides capacity for colder positions. Moving more KV to VRAM alone had negligible shallow-decode benefit. Using more pinned system RAM for repeatedly read recurrent snapshots would still incur PCIe traffic. Software layer placement can use the aggregate card capacity for workloads that need it. On this GPU pair and driver it still has to transfer activations without direct peer access, and the two tested DFlash2 placements failed to start cleanly. PCIe x16 describes the link. Peer access and decode throughput need their own measurements. [CUDA multi-GPU guide](https://docs.nvidia.com/cuda/archive/13.4.2/cuda-programming-guide/03-advanced/multi-gpu-systems.html) · [CUDA pinned-memory guidance](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html) · [HP Z440 QuickSpecs](https://h30434.www3.hp.com/psg/attachments/psg/Business-PC-Workstation-POS/48262/1/Z440%20QuickSpecs%20v36.pdf).

A larger single GPU is the more direct capacity upgrade for this workload if the installed PSU, connectors, case and cooling support it. HP lists 525 W and 700 W Z440 configurations. NVIDIA specifies 350 W board power, two PCIe 8-pin connectors and a 750 W reference system for the RTX 3090 Founders Edition. Actual Z440 PSU and cabling were not inspected. A third card also requires verified PSU headroom, cabling, slot clearance, and cooling. [HP Z440 QuickSpecs](https://h30434.www3.hp.com/psg/attachments/psg/Business-PC-Workstation-POS/48262/1/Z440%20QuickSpecs%20v36.pdf) · [NVIDIA RTX 3090 specifications](https://www.nvidia.com/en-eu/geforce/graphics-cards/30-series/rtx-3090/).
