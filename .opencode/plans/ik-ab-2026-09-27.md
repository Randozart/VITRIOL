## PLATFORM THESIS (evidence: 2026-09-27 ik unbuildability)
VITRIOL is the inference path for hardware the CPU-offload ecosystem has
left behind: pre-AVX2 workstations with modern GPUs and NVMe. Expert
compute stays on the GPU; the CPU is an I/O scheduler; storage becomes
the upgrade axis. CPU-offload forks (ik, upstream --n-cpu-moe) scale
their value WITH CPU modernity (AVX2 -> AVX512 -> Zen4); VITRIOL scales
with storage bandwidth and GPU. Evidence: ik_llama.cpp unbuildable on
the i7-3770 (Ivy Bridge) while the full VITRIOL pipeline runs; upstream
--n-cpu-moe on this box runs pre-AVX2 CPU kernels for expert GEMV.
Scope: applies to the over-VRAM streaming profile; resident inference is
CPU-generation-agnostic on any engine. The killer experiment (Arm U vs V)
tests the performance half of the thesis; the ik result proved the
compatibility half.

## GOVERNING PRINCIPLE (user directive, 2026-09-27)
VITRIOL is experimental. If ggml's or ik's stuff ends up better, we adopt it.
The A/B gates read as "best engine wins", not "defend the fork". Adoption
semantics per branch:
- upstream kernels win -> merge upstream, keep our server-layer work.
- ik wins on our models -> switch the ENGINE to ik; port what's ours
  (session router, kvtier - both server-layer, ik's server is same
  lineage). Drop diverged kernels, the custom store (ik --cpu-moe on the
  Optane file may make it redundant - that IS the killer experiment), and
  divergences ik supersedes.
- Engine-agnostic assets that survive ANY choice: the Optane session KV
  tier (files in llama_state_seq_save_file format), the session router,
  bench/probe discipline + scripts, ops layer (launcher, fingerprints,
  profiles, OOM hardening), and the research findings themselves.
- Standing feature justification (updated 2026-09-26): VITRIOL keeps only
  deltas that measurably win - currently MTP-on-qwen35, the session KV
  tier, the deep-context lifecycle, and the ops discipline. Everything
  else is dormant value (streaming) or hygiene.

## STAGE 4.5 (approved 2026-09-27): keep used experts resident - least-swap shape
  User directive: optimized shape = MoE experts resident in VRAM, swap as
  little as possible, all the benefit for the least loss. Design:
  1. DEV SPLIT FIX: extra_bufts ignores dev (all MoE on GPU0 today).
     Register per device; slots allocate on the computing device's pool
     (also eliminates inter-GPU expert copies).
  2. POOL SIZING: per-device pool = free VRAM at init - reserve
     (VITRIOL_POOL_RESERVE_MB, default 2300/device = 4.6G total for
     KV/dense/scratch). 24G rig -> ~15-16G pool = 9-16k slots vs the
     1440-slice working set (10x headroom -> zero steady-state eviction).
  3. HOT-SET PROTECTION: per-slot last-use timestamp; victim scan prefers
     slices idle > VITRIOL_LRU_HOT_MS (default 5000) before plain LRU.
     Cold bursts cannot flush the hot set.
  4. ACCEPTANCE: evictions/token -> ~0 after warmup; LRU hit rate -> >95%;
     decode >= store-historical 13 t/s on flash-next; bytes/token -> 0.
  Costs: VRAM headroom (262k ctx tight on flash-next; 32-64k fine);
  cold-start ~0.42 s per fully-cold token, declining with top-k overlap.
  Validation bed: HYBRID mode (same LRU pools, no store needed) - the
  2h store-as-file rebuild is NOT on the critical path for residency
  validation. Formal Arm V rerun (store-as-file) after.
  Ledger: 27B daily driver unchanged (already resident). Baseline being
  beaten: Arm U CPU-offload 0.5-0.8 t/s; store-historical 13 t/s.

## VERDICT (2026-09-27 ~10:4x): ik is UNBUILDABLE on this box - experiment pivoted
  Root cause chain: this host's CPU is an i7-3770 (Ivy Bridge, NO AVX2).
  ik's iqk_config.h auto-disables IQK_IMPLEMENT without __AVX2__, dumping
  ~12 iqk CPU files into stub paths that are THEMSELVES broken upstream
  (headers included inside the disabled guard; int-vs-long signature
  mismatches vs the extern-C declarations; unguarded AVX2 template code
  in iqk_quantize.cpp). Upstream explicitly supports only AVX2+ CPUs -
  we are the unsupported platform. Patches made locally (documented,
  4 edits to iqk_mul_mat.cpp / iqk_cpu_ops.cpp / iqk_common.h) got
  halfway; remaining work is stub-whack-a-mole with negative expected
  value. ik CUDA kernels themselves compile clean - but their showcase
  (hybrid CPU+GPU MoE) needs AVX2.
  PIVOT: the killer experiment proceeds with OUR fork on BOTH arms:
  - Arm U (upstream-style): our fork + --n-cpu-moe N (flag verified
    present, arg.cpp:2797) + model file on /scratch (Optane) +
    VITRIOL_MODE=off. This IS the "stock-path offload" baseline (our
    fork = upstream lineage; ik arm would have measured the same
    strategy with AVX2 CPU kernels we cannot use).
  - Arm V (VITRIOL store): VITRIOL_MODE=stream store arm (+ -ub probe).
  - GLM-5.3-Flash 3.0bit (downloaded, 109.4 GiB): Arm U first - answers
    "can this box run a ~290B-class MoE locally" directly.
  ik-related follow-ups worth keeping: report the broken main + pre-AVX2
  stub breakage upstream (courtesy); their GDN fused + recurrent
  checkpoint PRs remain pillage candidates INDEPENDENT of the build
  (port to our fork when the cliff hunt resumes).
