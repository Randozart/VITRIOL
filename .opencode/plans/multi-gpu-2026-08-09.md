# Multi-GPU Plan: GTX 1070 Ti + RTX 3060 unified layer split

Date: 2026-08-09
Status: in-progress (3060 arrives later; code validated on single 1070 Ti now)
Location: `.opencode/plans/multi-gpu-2026-08-09.md`

## Question

Link two mismatched GPUs (GTX 1070 Ti 8GB sm_61 + RTX 3060 12GB sm_86) into a
unified VRAM pool. Cheapest possible hardware purchase?

## Verdict

- **$0.** llama.cpp already implements layer-boundary device handoff natively:
  `LLAMA_SPLIT_MODE_LAYER` (default) + `--tensor-split`. Layers are assigned to
  devices proportionally to free VRAM (`llama-model.cpp:1217-1258`). The ~8 KB
  residual-stream activation crosses the device boundary through host memory in
  microsecond time. Motherboard PCIe bus IS the fabric — no PLX switch, no FPGA,
  no NVLink, no riser required if two slots fit the cards.
- Misconceptions corrected:
  - Vulkan Device Groups cannot link mismatched cards — the driver only reports
    NVLink/SLI-chained groups. Not a bypass.
  - CUDA P2P is not a hard blocker for the split — llama.cpp's host-staged copy
    never needs P2P.
  - USB x1 mining riser: chokes PCIe to ~1 GB/s. Negligible for the tiny handoff,
    catastrophic for out-of-core MoE weight streaming (`VITRIOL_MODE=stream`).
    If a riser is needed, buy a true x8/x16 ribbon ($15-25).
- Architecture constraint: Pascal sm_61 has no FlashAttention and 1/64-rate fp16
  math. Keep attention-heavy/KV/head layers on the 3060; llama.cpp auto-split by
  free VRAM already trends that way (3060 12GB > 1070 Ti 8GB).

## Implementation stages

1. `probe.rs` — enumerate all GPUs via `nvidia-smi --query-gpu=index,name,memory.total,compute_cap,pcie.link.gen.current,pcie.link.width.current --format=csv,noheader`; build `gpus`, `gpu_count`. CSV has spaces in names → split on commas, not whitespace.
2. `estimator.rs` — `vram_total = Σ gpus[].vram_mib`, `oh = Σ gpu_overhead(cc)`. Single-GPU result must be byte-identical to today.
3. `vitriol-cuda-integration.cpp`:
   - `LRUKey` gains `int device`.
   - `g_lru_pool/slot_size/num_slots/pool_size/stream/slot_events` → `[GGML_CUDA_MAX_DEVICES]`.
   - `g_pin_pool/offset/total` → per-device.
   - `g_output_cache_pool/size` → per-device; data_dev pointers assigned at store time into current device pool.
   - Resolve device via `cudaGetDevice` (self-contained; no ggml internal dependency). Set device before any `cuStreamCreate`/`cuMemAlloc`/`cuMemcpy*`; restore after.
   - Cleanup iterates devices with `cudaSetDevice` before `cuMemFree`.
   - Single-GPU behavior collapses to existing code path (guard `if dev==0` not needed — arrays of size 1 behave identically).
4. `vitriol_shim.py` — thermal guardrail polls all GPUs, returns max temp.
5. `sweep_controller.py` — `--devices` knob forwarded into server env (no-op when one GPU).
6. Build + `cargo build --release`; verify single-GPU no regression via known pin sweep baseline (9.6–9.98 t/s).

### Extra fix found during implementation

`llama-model-loader.cpp` forced ALL `exps.weight` tensors into the **device-0** VITRIOL buffer type via `vitriol_get_expert_buffer_type()`. Under a multi-GPU layer split that would misplace GPU1's experts. Added `vitriol_get_expert_buffer_type_dev(int)` and a loader resolver that walks the per-layer buft list, finds the owning CUDA device handle (`ggml_backend_reg_dev_get(cuda_reg,i)` match), and asks for that device's buffer. Single-GPU resolves to device 0 → identical behavior.
