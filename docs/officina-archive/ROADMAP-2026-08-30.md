## Purpose

Pre-register the success criteria for the project thesis — "Trismegistus is
a better daily driver than OpenCode, Hermes, or little-coder for our
purposes (local 27B, ~11 t/s, hard 54K window, local-first)" — so the R3
dogfood day is graded against claims written BEFORE the experiment, not a
narrative fitted after it (Rule 3: hypothesis and verification stated first).

This document POINTS, it does not copy: findings live in
`docs/AUDIT-2026-08-30.md` (F-numbers), policy in
`docs/RULES-CACHE-POLICY.md`, progress in `POST-MIGRATION-PLAN.md`.

## The four pillars (testable claims + verification)

**P1 — Enforced budget.** Claim: only Trismegistus enforces a hard token
budget as configuration law; the components only observe cost.
*Verified when:* §R2.8 amended with measured rows (F4); fixed overhead
≤ 8K tok in the ledger; injection budgets enforced in code and present in
the validator inventory.

**P2 — Continuity of code AND context.** Claim: work survives
interruptions better than any component alone (crash → warm KV restore;
rewind restores worktree and context from one turn key).
*Verified when:* during dogfood, an engine restart resumes warm via slot
restore; `/rewind N` runs for real in a session; no re-prefill-from-zero
event goes unexplained in the cache panel.

**P3 — Governance over instruction.** Claim: executable gates catch what
prose rules cannot on a 27B Q3.
*Verified when:* gates demonstrably fire and are honored in dogfood (perms
denials, validate catches, praetor hooks installed everywhere — F8); every
audit finding carries a disposition (FIXED/ACCEPTED/DEFERRED); zero
config-lies remain open.

**P4 — Attackable overhead.** Claim: fixed overhead is measured and
reducible on demand — not a fixed property of the stack.
*Verified when:* `prompt-size --json` before/after the diet shows the
delta; ledger tok/task reflects it; the cache/bust panel shows real hit
behavior (the 7,870 → 1,722 signal, panelized).

Grading: at the dogfood day, each pillar is marked HELD / PARTIAL / BROKEN
with ledger evidence. A BROKEN pillar is a finding, not a failure of the
document.

## Execution order — trustworthy → differentiated → proof

**Tier A — machine trustworthiness** (pre-reboot, no sudo): audit fixes
F3, F1, F11, F4, F2, F9, F10, F8, F12, F6, F7, F5-prep — in that order
(measurement integrity first, then safety boundaries, then hygiene).
Rationale: every "better" claim is measured by machinery that F1/F3 would
corrupt, and dispatch safety (F11) must precede any gateway exposure.

**Tier B — differentiators**: RULES-CACHE-POLICY §3 implementation
(rules-index compiler, residency knobs, cache panel — compiled through our
own AGENTS.md first), toolset/skill diet to fixed ≤ 8K, interactive
acceptance (`tris code`/`tris chat` PTY smoke), Telegram e2e if adopted,
`hermes backup` timer, mongod-vitriol decision.

**Tier C — proof** (owner's Track A, staged): 27B CERT boot → vision
end-to-end → R3 baselines → R3.5b concurrency sweep → dogfood day →
pillar grading.
